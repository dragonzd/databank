# Step 2: 软件架构与技术方案 — 数据银行系统平台技术方案

## 1. 技术方案概述

构建一个「五层协同 + 事件驱动微服务」的混合架构：联盟链作为信任锚点，隐私计算作为安全执行环境，事件总线串联业务服务，边缘 SDK 实现"计算路由到数据"。

## 2. 系统架构设计

### 2.1 限界上下文（DDD Bounded Context）

- Identity Context: DID 管理、VC 签发/验证、鉴权方注册、信誉质押
- Account Context: 协议账户、三权令牌、生命周期、纠纷仲裁
- Settlement Context: Token 发行、计量计费、分账引擎、出入金网关
- Storage Context: 边缘节点管理、加密分块存储、CRDT 同步、完整性验证
- Privacy Context: TEE 运行时、MPC 引擎、联邦学习、同态加密
- Marketplace Context: 隐私索引、需求撮合、交易所、衍生品
- Finance Context: 数据理财、资产入表、贷款风控、RWA 管理
- Governance Context: 监管合规、审计日志、参数治理、升级管理

### 2.2 核心数据流

用户设备(边缘 SDK) → 加密分块 → 边缘存储节点 → Merkle 证明 → 存储验证 → 链上锚定
协议账户合约 → 鉴权方背书 → 隐私索引服务 → 使用方需求 → TEE 安全沙箱 → 使用方获取结果 → TEE 计量上报 → Token 结算引擎 → 自动分账 → 数据所有方/鉴权方/银行

### 2.3 模块间接口

| 接口 | 方向 | 协议 |
|------|------|------|
| SDK → Storage Node | 上行 | gRPC + Protobuf |
| Storage Node → Verifier | 内部 | gRPC |
| Verifier → Account Contract | 链上 | Substrate Extrinsic |
| Account Contract → Settlement | 链上事件 | Event → Kafka |
| Privacy Index → TEE Runtime | 内部 | gRPC |
| TEE Runtime → Settlement | 内部 | Kafka |
| Settlement → Payment Gateway | 外部 | REST API |
| Open API → All Services | 对外 | REST + WebSocket (Kong/APISIX) |

## 3. 技术选型与 ADR

### ADR-001: 联盟链选型 → Substrate

状态：已接受。选择 Substrate（而非 Hyperledger Fabric 或自研链），因为高度可定制、ink! 合约、原生 DID 托盘。代价：团队需要 Rust 能力。

### ADR-002: 事件总线 → Kafka

状态：已接受。Kafka 持久化日志模型天然适合结算审计（不可篡改事件流），吞吐量满足交易所场景。代价：运维复杂度较高。

### ADR-003: 隐私计算 — 数据沙箱统一范式，TEE/容器分级 + MPC 补充

状态：已接受。以「数据沙箱（模型进场、数据不出域）」为统一执行环境——数据使用方授权数据鉴权方将模型放入沙箱，基于数据所有方授权开放的数据完成训练与推理，全程数据不出域，按使用量与时长计费、设定沙箱有效期，到期自动回收销毁。

- 隔离分级：L1 Docker 容器沙箱（断网 + 审计）承接低敏感数据；L2 TEE 可信执行环境承接高敏感数据；L3 MPC/联邦学习支撑跨机构联合建模。
- 安全闭环（七道闸）：授权网关、模型保护、网络隔离、结果闸门、精确访问控制、可信计量、可验证销毁。
- 演进路径：MVP 先上 L1 容器沙箱，第二阶段引入 L2 TEE + 差分隐私，第三阶段按需接入 L3 MPC/联邦学习。

## 4. 数据模型设计

### ProtocolAccount

- account_id, owner_did, ownership_token, usage_licenses[], revenue_certificates[]
- data_manifest: MerkleRoot, lifecycle_state: Enum, endorsements: [(DID, Confidence)]

### SettlementRecord

- txn_id, account_id, consumer_did, usage_metrics{data_volume, duration, compute_units}
- token_amount, split{owner_share:70%, endorser_share:20%, bank_share:10%}
- block_height, timestamp

### EndorserProfile

- did, staked_tokens, total_endorsed, dispute_rate, confidence_score(0-100), revenue_accumulated

## 5. 关键技术难点

| 难点 | 解决思路 |
|------|---------|
| 数据不转移可用计算 | TEE 远程 attestation + 加密传输到安全沙箱，计算后仅返回结果 |
| 计量公平性 | TEE 内计量，数据与计算资源双维度计费，异常行为链上举报 |
| CRDT 冲突解决 | LWW+操作转换 CRDT，Merkle DAG 保证最终一致 |
| 冷启动信任 | 机构信誉+质押混合模型，第三方评级机构交叉验证 |
| 监管兼容 | 监管节点，地域标签，合规策略可插拔 |

## 6. 非功能需求

| 维度 | 目标 | 方案 |
|------|------|------|
| 性能 | 结算 P99<500ms，API P99<200ms | 链下批处理+链上锚定，API 网关缓存+限流 |
| 可用性 | 99.99% | 多活部署 3AZ，Istio，自动故障转移 |
| 安全性 | 零信任 | mTLS 全链路，TEE 硬件隔离，合约形式化验证 |
| 可扩展性 | 百万级账户 | 合约分片，存储水平扩展，Kafka 分区 |
| 可观测性 | MTTD<1min, MTTR<15min | OpenTelemetry，Prometheus+Grafana，ELK |
| 合规 | 数据安全法、GDPR | 监管节点，地域标签，审计日志不可篡改 |

## 7. 技术风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| TEE 侧信道攻击 | 高 | 定期固件更新，多 TEE 冗余对比 |
| 联盟链治理僵化 | 中 | 链上治理模块可升级 |
| 边缘 SDK 碎片化 | 中 | 核心 Rust + 平台绑定层，C ABI 兼容 |
| Kafka 集群运维 | 中 | 托管 Kafka 或 Redpanda 降低运维负担 |
